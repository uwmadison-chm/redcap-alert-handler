# Design Doc: Realtime REDCap Alert Processor (`rah`)

A Python utility that processes email generated by REDCap in close-to-realtime,
using an Office 365 mailbox as a durable message queue accessed through the
Microsoft Graph API.

## What This Is

This is an application-level event processor whose queue is an O365
mailbox. It provides access to multiple processors, depending on message content, to
process messages differently.

O365 mailboxes are not designed to be queues! So we do need to think carefully about how
we process them to make sure we neither miss, nor repeat, actions we want to take.

## Why Would We Do This

REDCap has poor support for realtime export of data. They have a webhook system in Data Entry Triggers; however, this webhook fires on **every single data change** and the change itself blocks on the server's response, with a five-second timeout. A webhook server failure immediately brings a project to its knees.

And in the very best case, a busy project is going to generate countless Data Entry Triggers that no one ever needs to see. And the data contained in a DET payload is not configurable at all, so nearly every DET request would need to be followed by a request to the REDCap API.

Alerts and Automated Survey Invitaitons, however, can be targeted based on project logic. They can be configured to contain needed information. And they are normally delivered via email. In my testing, Alerts and ASIs from our REDCap server were delivered to my campus O365 inbox's web interface within 2-6 seconds.

## Example applications

* Assign participants to a group during a survey flow, using an arbitrary ML model.
* Send an intervention message based on a survey response (again, arbitrary model).
* Convert email-based alerts to web-push alerts.

When configured correctly this handles data in a HIPAA-compliant way. In our
environment, REDCap → internal O365 mailbox email is compliant. Note that PHI
therefore lives in *every* folder this tool touches, including `dead-letters` —
retention policy must cover all of them, not just the live inbox.

## Design overview

* A single long-running process uses OAuth to obtain a token and watches the
  inbox of an O365 service account via `msgraph-sdk-python`.
* It reads a TOML config describing a collection of studies. Each study entry has
  at least:
  * a unique **slug** (the key);
  * a **maximum age**, so old mail isn't mishandled after an outage;
  * a **handler reference** (a registered entry-point name — see below). This is
    many-to-one: several studies may reference the same handler. A handler is not
    owned by a study and must not assume it serves exactly one.
  * an optional **timeout** (falls back to a global default).
* For each incoming message, the subject must begin with a study slug, optionally
  followed by `|`. If it doesn't match a known slug, the message moves to
  `dead-letters`. Otherwise the message is dispatched to the handler the study's
  config references (possibly shared with other studies).
* Based on the outcome, the message moves to `{slug}/completed`, is left for retry,
  or moves to `{slug}/error` / `dead-letters`. The handler also performs the
  side effects we actually want.

### What Graph Offers

Graph gives a stable immutable message identity and an atomic `move` (one REST
call; it either lands in the new folder or it doesn't), avoiding IMAP's
UID-reassignment headaches. It doesn't have transactions, so we can't do a thing like "claim a message, run a thing, and move the message." So idempotency is
mandatory in processing messages.

## One Watcher Only

Exactly one watcher claims and moves messages. Graph cannot atomically *claim* a
message for one of several competing readers, so we do not try. For throughput,
fan out **inside** the process (one reader, a worker pool); the claim/move logic
stays in one place. Treat single-writer as an invariant, not a configuration knob.

## State model: four layers, each with one job

1. **`internetMessageId`** (the RFC `Message-ID`) — the durable idempotency key.
   It is stable across moves and folders, unlike the Graph `id`, which *changes*
   when a message moves between folders. Handlers receive this and use it to
   detect replays.
2. **Single-value extended properties** — the loop's *authoritative* machine state:
   retries-left, retry-time, processed marker. Typed, survive moves, read via
   `$expand`.
3. **Categories** — an *advisory, derived, human-visible* projection only
   (e.g. `rah:processing`, `rah:errored`, `rah:dead`). Set as a side effect of the
   real state transition so the service-account mailbox is legible in Outlook.
   **Never read back as input.**
4. **Folder** — where the message physically lives, for human triage.

**Ordering rule:** write the authoritative property *first*, then the advisory
category. The property is always authoritative; if a category and property
disagree after a half-completed write, the property wins and the category is
corrected on next touch. This keeps the convenience layer from ever becoming
load-bearing.

Pre-seed the mailbox's master category list once so the `rah:*` labels render
with color (undefined categories are still readable via Graph but show without a
swatch).

## Idempotency (mandatory)

Because "side effect + move" is not transactional, a crash between a completed
side effect and a completed move will cause reprocessing. Handlers **must** be
idempotent. The contract: a handler records that it has processed a given
`internetMessageId` in its own store and short-circuits on replay. This is the
real correctness backstop and survives crashes, replays, and dead-letter
reprocessing. The folder-topology check ("is it already in `{slug}/completed`?")
is at best a reader-loop optimization, never a correctness mechanism.

## Handler contract

Handlers are **functions**, discovered as plugins via entry points. A handler
package declares itself under the `rah.handlers` group in `pyproject.toml`; the
loader uses `importlib.metadata.entry_points(group="rah.handlers")` to resolve a
config-named handler. This gives install-time validation and avoids `sys.path`
games. Entry points are the *only* discovery path — a handler must be a registered
entry point in an installed package, full stop.

The handler receives the parsed body, the `internetMessageId`, and a context
object that **must** include the invoking **slug** and that study's config entry —
because a handler may serve several studies, it cannot infer which one invoked it
from its own identity. A handler that branches on study (different model, group
assignments, intervention copy) reads the slug from the context; a purely
content-driven handler can ignore it. (Settling the exact context shape is the
open question below — but the slug is a fixed requirement.)

A note for shared handlers that keep their own idempotency store: the dedup key
stays `internetMessageId`, which is globally unique, so the store is keyed by
message, not by study. Don't partition it per-study — that quietly reintroduces
the one-handler-per-study assumption through the back door.

Outcomes are signalled by **exceptions**, with a hierarchy we own:

* **clean return** → completed → move to `{slug}/completed`;
* **`TransientError`** → leave for retry (decrement retries-left, set retry-time);
* **`PermanentError`** → dead-letter / `{slug}/error`;
* **any other unhandled exception** → treated as **transient + attempt-counted**.

Mapping unexpected exceptions to transient (rather than permanent) is deliberate:
treating unknown bugs as permanent would let a deploy bug silently discard real
messages. The poison-message guard (below) ensures a genuinely bad message still
terminates instead of looping forever.

## Poison-message guard

A handler that *crashes* on a specific message would loop forever if the message
stayed put. The extended-property retries-left counter, decremented on each
transient/unexpected failure, forces the message to `dead-letters` once it hits
zero.

## Deployment & handler distribution

To deploy, you'll 

* **`rah`** (public) — the engine. A normal Python package: defines the
  `rah.handlers` entry-point group as a contract, exposes the handler protocol
  and the `HandlerError` / `PermanentError` / `TransientError` hierarchy for
  handlers to import, ships the CLI. Knows nothing about any real study.
* **Handler packages** (private, one per study or per group) — each its own uv
  project that depends on `rah`, registers its handlers under `rah.handlers`, and
  declares its own deps (e.g. an ML stack). Contains internal study information,
  so these stay private and are versioned independently.
* **Deployment project** (`our-rah`, private) — a thin composition root with
  essentially no code of its own. Its only job is to pin the combination: a known
  `rah` version plus the handler packages this deployment runs.

```toml
# our-rah/pyproject.toml
[project]
name = "our-rah"
dependencies = [
  "rah @ git+https://github.com/your-org/rah.git@v0.3.0",
  "study-acme-handlers @ git+ssh://git@github.com/your-org/study-acme-handlers.git@v1.2.0",
  "study-beta-handlers @ git+ssh://git@github.com/your-org/study-beta-handlers.git@v0.4.1",
]
```

`uv sync` builds one shared environment containing `rah`, the handler packages,
and all transitive deps; `rah watch` runs inside it and discovers handlers via the
entry points the handler packages declared.

How the pieces resolve:

* **`rah`** — pinned as `rah @ git+https://…@vX.Y.Z`. Because the repo is public,
  this is an unauthenticated HTTPS clone (no key needed). If `rah` is ever
  published to PyPI, this simplifies to a plain `"rah"` version spec.
* **Handler packages** — pinned as `… @ git+ssh://git@github.com/…@vX.Y.Z`. uv
  clones over SSH, so private-repo access is just the box's deploy key or the
  operator's SSH agent — nothing public, no package registry to run. Pinning to a
  tag or commit gives reproducible deploys. (A private index — Azure Artifacts,
  self-hosted PyPI — is an option later but is more infra than this scale needs.)
* **Dev loop** — for handler development, swap a git pin for an editable path
  install (`uv add --editable ../study-acme-handlers`) so source edits land on the
  next `watch` restart without reinstalling.

The deployment project's **`uv.lock` is the deploy manifest**: the exact resolved
versions of `rah`, every handler, and every transitive dep, committed. That is the
reproducible-deploy and rollback story — revert the lockfile, `uv sync`, restart.
Adding a study is a one-line dependency edit; removing one deletes a line; bumping
a handler changes its pin. None of it touches `rah` or the other handler repos.
"Which studies does this box run?" is answered entirely by `our-rah`'s
dependencies. Staging vs. prod, or one box per study group, are just different
deployment projects (or tags/branches of one) pinning different handler sets
against the same `rah`.

Two consequences to keep straight:

* **The entry-point contract is now a versioned, cross-repo API.** Once a private
  handler repo pins `rah@v0.3.0` and does `from rah import TransientError`,
  changing the handler signature, the exception hierarchy, or the context object
  is a breaking change for repos `rah` may not see. Version that contract
  deliberately (semver + a documented "handler API" section), rather than letting
  it drift.
* **Secrets live *around* the deployment project, not inside the pins.** `our-rah`
  pins *what code runs*; the runtime environment (systemd unit, container env)
  supplies the secrets and paths it runs against — token store location,
  tenant/client IDs (the same items in the config-vs-env split). Keeping these
  separate lets the deployment project itself stay boring and committable without
  leaking credentials.

Reminder from the handler-contract section: entry points are discovered at process
start, so handlers are **not hot-reloadable**. "Deploy a handler" = install/pin +
restart `rah watch`. Shared environment is the assumption (all handler deps
coexist with `rah`'s); if incompatible deps ever collide, the escape hatch is the
subprocess-handler bridge — a thin in-env handler shelling out to a
separately-managed venv — trading the in-process function contract for isolation.
Not worth building now.

## Message format

Not specified by this layer; whoever writes the Alerts/ASIs and the handlers must
agree. Default plan: TOML in the `text/plain` body. JSON or HTML-encoded bodies
are permissible. Because we're on Graph for everything else, prefer reading the
body via Graph's message representation rather than reconstructing MIME.

The `{slug}|…` subject form also allows passing data in the subject. Any
modifiable part of the message *may* be used, but note that `From`/`Reply-To`
display names are fragile — Exchange rewrites/normalizes headers more than you'd
expect. The subject slug and the body are the trustworthy channels.

## Ordering

There is **no** processing-order guarantee (arrival order is not processing order
under any failure/retry). Handlers must not assume sequence.

## Config vs. environment

* **Environment:** secrets and deployment-specific paths — token store location,
  tenant/client IDs.
* **TOML:** study definitions and operational policy — slugs, handler refs,
  per-study timeouts, max-age.

## CLI entry points

Multi-command, git-like, built with **Click** (`@click.group()` + subcommands):

* `rah auth` — runs the O365 OAuth flow; stores tokens at a location given by an
  environment variable.
* `rah watch` — starts the single long-running reader/dispatcher.
* `rah replay` — reprocesses `dead-letters` **on demand** (the usual cause is a
  missing/wrong config; a human should fix config before replaying). Not
  automatic. Dead-letter retention/age-out is a policy decision and, being PHI,
  is covered by the retention policy.
* `rah health` — writes a status report to stdout (TOML or JSON) exposing at least
  backlog depth, oldest-unprocessed age, and per-study error counts.

## Timeouts & concurrency

Per-study timeout (global default fallback) is **mandatory** — a hung handler
otherwise stalls the single-reader queue completely. Worker-pool fan-out keeps the
reader loop responsive while handlers do slow network/ML work.

## Open questions

* Exact shape of the handler context object (slug and study config entry are
  fixed requirements; what else it carries is open).
* Where the per-handler idempotency store lives (handler-owned, but do we offer a
  helper/default?).
* `rah replay` selection semantics (all dead-letters? filter by slug/age?).
